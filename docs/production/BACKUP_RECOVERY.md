# Encrypted Backups, Restore & Disaster Recovery

## What is protected

- **Live:** host bind-mounted `data/pool.sqlite` with possible `-wal` and `-shm` sidecars; one Node backend is the writer.
- **Local:** `backups/pool-<UTC>-<nonce>.sqlite.gz.enc`; generated by `backend/src/backups.ts` from SQLite's online backup, gzip then AES-256-GCM (the `F1BK` envelope). Files are mode `0600`.
- **Offsite:** root-owned host rclone cron copies encrypted snapshot files to a private OCI S3-compatible bucket in the authorized region. The remote is an **independent recovery copy**; cloud billing/retention rules apply.
- **Secrets:** `BACKUP_ENCRYPTION_KEY` (64 hex characters) is **not** stored in the backup file. Without it, restoration is impossible. Keep a protected recoverable key copy in a password manager separate from the VM.

## Verify every layer, not just the file name

```bash
cd /opt/f1/f1-prediction-pool
ls -lt backups/*.sqlite.gz.enc | head               # filenames/metadata only
sudo crontab -l                                     # confirm scheduled copy
sudo rclone --config /home/ubuntu/.config/rclone/rclone.conf ls 'oracle-s3:<OCI_BUCKET>'
```

Do not print `.env`, encryption keys or OCI credentials. Local snapshots after a process stop/publication are not evidence that the nightly copy succeeded. Prefer `rclone copy` and explicit retention over `sync`, which may remove remote snapshots not present locally.

## Controlled restore (maintenance window)

**Before restoring:** identify the approved recovery point, affected users/ledger, and compatible backend commit. Announce downtime, preserve existing database files elsewhere on the host, and stop the writer. Restoring old records will **discard changes made after that snapshot**; do not start a second API process during the procedure.

```bash
cd /opt/f1/f1-prediction-pool
docker compose stop backend
# Select exact approved object; do not bulk-download the private bucket:
SNAPSHOT_FILE='pool-<UTC>-<nonce>.sqlite.gz.enc'
sudo rclone --config /home/ubuntu/.config/rclone/rclone.conf copyto \
  "oracle-s3:<OCI_BUCKET>/$SNAPSHOT_FILE" "./backups/$SNAPSHOT_FILE"
# Privileged rclone may have downloaded the file as root; make THIS file readable to UID 1000:
sudo chown 1000:1000 "./backups/$SNAPSHOT_FILE"
# Restore with Node 22 rather than the Ubuntu host's potentially older Node:
docker run --rm --user 1000:1000 --env-file .env \
  -v "$(pwd)/data:/app/data" \
  -v "$(pwd)/backups:/app/backups:ro" \
  -v "$(pwd)/scripts:/app/scripts:ro" \
  node:22-bookworm-slim node /app/scripts/restore-backup.mjs \
  "/app/backups/$SNAPSHOT_FILE" /app/data/pool.sqlite
# Confirm file owner and open normally:
sudo chown -R 1000:1000 data backups
docker compose up -d backend
curl --fail --silent --show-error http://127.0.0.1:8081/api/health
```

**Important:** the source PDF describes a root rclone remote at bucket root. If your private inventory configures an additional prefix, include it explicitly when selecting the exact snapshot; do not guess paths. Do not use an unverified backup file or store its key in shell history.

## Post-restore validation

1. Confirm health/containers, correct app commit, and recent SQLite errors absent.
2. Run `PRAGMA integrity_check` and `PRAGMA foreign_key_check` using a controlled maintenance tool / isolated clone of the DB, **not an arbitrary public SQL shell**.
3. Verify a real tournament's members, published scores, lock times and financial ledger totals in the app (read-only), and compare with the expected snapshot time.
4. Validate Gmail outbox state; note that already delivered emails may requeue following a historic restore. Avoid accidental mass resend.
5. Record actual data loss window (RPO), downtime (RTO) and operator approval. Test a new encrypted post-restore snapshot and offsite replication.

## Backup key and OCI customer-key rotation

- Encryption keys for **existing** snapshots must be retained in a protected key archive even after active key rotation; never simply overwrite the old key with no recovery mechanism.
- If an OCI S3 customer secret key was revealed by `rclone config`, revoke/rotate it in OCI user Profile → Tokens and keys → Customer secret keys. Edit the protected rclone config without echoing plaintext; validate `rclone lsd` then revoke the old key.
- A full-VM loss also requires the protected externalized `.env` backup and credentials. If you encrypt an env bundle separately, use a modern authenticated encryption tool where available; the supplied PDF's OpenSSL AES-CBC/PBKDF2 example is **not authenticated encryption** and must be integrity-verified separately.

## Disaster recovery drill

At least monthly, restore a selected encrypted backup into an isolated temporary database/VM with no public exposure and disabled email delivery. Verify the auth session schema, tournament count, results, ledger accounting, and `foreign_key_check`, then securely delete the test copy. A successful rclone `ls` only proves an object exists—not recoverability.
